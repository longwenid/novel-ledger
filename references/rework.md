# 返工与成本：架构上怎么让写作少返工

对象：独立会话写审的返工。本文只谈**引擎可以负责的那一半**——不讨论模型能力，只讨论"同样的缺陷为什么会反复出现，
以及结构上怎么让它第一次就不出现或第一次就被挡住"。数据来自一次真实的三章完本运行
（`validation/quality-run-2026-10-17.md`：81 次派工里只有 3 次执笔，59 次发生在第一个字之前）。

## 一、先把返工分类（实测）

| 类别 | 实机例子 | 谁最终发现 | 单轮代价 |
|---|---|---|---|
| 机械：形状/引用/字数/禁区 | 世界记录缺 links、领域为空 | preflight 或审查者 | 一次返修 + 一次独立审 |
| 机械：数字与关系算不平 | 3 次×17 年写成 17 年；六/四/七份与十七份对不上 | **独立审查者**（引擎没查） | 一次返修 + 一次全量重审 |
| 判断：首稿达不到判据 | 世界写了 55 条没人读的记录；骨架漏节点；卷纲账目不全 | 独立审查者 | 同上 |
| 判断：内部自相矛盾 | 同章"左耳空了"与"声音落在左边"；市局/分局号段冲突 | 独立审查者 | 同上 |
| 过程：返修变成重写并回退 | 世界前两轮返修把全部记录重写，已过的 findings 又回来 | 下一轮审查者 | **双倍**：重写 + 重审 |
| 过程：控制面churn | 11 次取消、4 次 `revision_blocked`、先派工后裁决导致任务作废 | 主控 | 一次白派 |
| 形态：作品形态无处表达 | 作者要三章完本，档位表最小 14 章 | 无（被另一个 bug 掩盖） | 整条收尾路径 |

结论：**前两类和第五、六类不是"审查层不够强"，而是"引擎本可以自己判定"**。返工的大头来自"判据没有前移"和
"返修没有被约束成窄改"。

## 二、四条机制（对应上面的分类）

### 机制 1：判据前移——审查者的清单，生产者先看一遍（已落地）

- 同一个表 `CHECK_SETS` 既渲染审查者的清单，也渲染生产者的"提交前自检"（`briefs.self_check_block` +
  `SELF_CHECK_HINTS`），逐条写成生产者能自己回答的问题。
- `check`/`preflight` 与 `submit` 走**同一批校验**（`workflow.apply` 在预览事务里跑），所以简报里说的
  "机械项提交时直接判"是真的：形状、引用、字数、禁区、节点窗口、世界域表、局部返修范围都在试算阶段拦下。
- 守卫：`test_the_producer_brief_carries_the_rubric_the_reviewer_uses` 要求"生产者被判的每条判据都有自检一行"，
  两个方向都不许漂移——清单改了而简报没改会红。
- 效果方向：把"只能靠独立会话发现"的缺陷压到"生产者自己就能发现"。这是唯一在**不增加派工**的前提下减少返工的机制。

### 机制 2：返修范围守卫——局部返修只能是窄改（已落地）

- `workflow.require_narrow_repair`：当 findings 全是 `local`、且能在候选里认出被点名的记录/节点/章时，
  **没被点名的部分必须与上一版逐字一致**；改动或删除即拒（`repair_scope`，错误里列出漂移项与已点名项）。
- 放宽条件写在实现里：`chapter`/`volume` 范围放行；findings 认不出目标时不做猜测（fail-open，不制造假拒绝）。
- 效果方向：① 重写被挡在提交那一刻，不消耗独立审查；② 已过的 findings 不会被顺手改回去（实测世界前两轮正是这样丢的）。
- 守卫：`test_a_local_repair_may_only_change_what_its_findings_name`（含放行与拒绝对照）。

### 机制 3：让账目结构化，引擎才能算（**未落地，下一步**）

实测三个不同阶段的缺陷是同一类：**数字与关系散在叙述里，只有人读得出来**。

- 契约里的体量是结构化的，所以 `creation.validate_contract` 能机械判"章数与档位相容"；
- 而"六次垫付×3 岁=18 年""17 份=6 份年岁+11 份手续""六/四/七分章"全在散文里，只能靠审查者算。

设计：给设计/卷纲/章计划加一个**可选但一旦给出就机械校验**的 `ledger` 块：

```json
{"ledger": [{"key": "承役缺额总数", "value": 17, "sum_of": [6, 11]},
            {"key": "垫付累计年数", "value": 18, "product_of": [6, 3]}]}
```

- 引擎只用四种关系（`sum_of`/`product_of`/`equals`/`ratio_of`），逐个求值；算不平就在提交时拒，并给出期望关系。
- 它是**可选**的，所以不强迫所有项目填；但一旦填了，后续工件（卷纲、章计划、章审的 facts）读同一个键，
  跨工件不一致立刻可见——这正好覆盖"只有审查者能发现"的那一类。
- 代价：模板、payload 字段、简报各加一条；风险是又变成"要求生产者多交东西"。所以先做成"可选+只在填了时校验"。

### 机制 4：把审查发现回流成判据（**未落地**）

机制 3 到位之后，"审查者发现的数字矛盾"可以固化成机械判据：同一条关系第二次出现时，引擎先算一遍。
更一般地，每一条 `quality` finding 都可以标注"这条本来可否机械判定"，一段时间后据此补 `check` 项。
这是把"审查经验"变成"引擎能力"的唯一可持续路径。

## 三、还已有的两条（本轮之前修掉，仍在生效）

- **停止点必配作者通道**：`workflow.STOP_POINTS` + `AUTHOR_CHANNELS` 登记每个停止点的通道，
  守卫断言登记项仍在代码里。三次实机死路（世界候选、第三章、修订范围外缺陷）都因此可继续。
- **状态与投递不变量**：`book_state.check_state`（运行/暂停与接受条目一致）、在途任务版本一致、
  必读无重复、投影仅在源不在场时必读、每阶段必读材料必须声明。

## 四、设计原则（给以后加功能的人）

1. **能机械判定的，不要交给独立会话。** 独立会话是稀缺资源：一次派工 = 一个会话 + 一份完整材料 + 一次全量重审。
2. **判据只有一份。** 简报与校验、生产者与审查者必须读同一张表；两处各写一遍，迟早互相漂移
   （世界域表就是这个例子：简报说"按体量缩小"，校验说"十个领域都要"）。
3. **返修是窄改，不是重写。** 让引擎能认出"没被点名的部分"，并拒绝改动它；宽范围要由 findings 明确声明。
4. **停下来必须有人说了算。** 任何"引擎不再自动往下走"的位置都要有结构化作者决定，选项里必然包含
   "接受并记为未解决项"（可见、不等于通过）。
5. **形态要能表达。** 引擎写死的合法性边界（档位章窗）必须覆盖作者可能提出的形态，否则会出现
   "能改到、能写完、但关不掉"。
6. **成本是设计输入。** 每加一份必读材料、每加一层审查、每加一个字段，都要能说清它换回了什么；
   本轮把这件事变成可复跑的账（`validation/run_analysis.py` 等探针）。

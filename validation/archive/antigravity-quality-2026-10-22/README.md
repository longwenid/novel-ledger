| 类型 | 可定位的正文现象 | 对应的架构缺口 |

| 场景与地点 | 36章入管出发，37章回工坊整备；52章冲进中环法庭，53章回外环泵房；同一工厂从第七外环第十二井变成第四外环第七井。 | 粗粒度地点和空 places 变化无法覆盖具体动作；没有“退出/到达/完成”状态，也不主动查未申报的新事件。 |

关于债务：第9章确有十日展期，45/58章有总括清债，不能说债务从未解决；不同债权人、币种、金额与期限之间缺少桥接。关于穿越称谓：前文已有“两世/原身”的可闻线索，不能说配角完全无从知情；稳妥判断是缺少披露与接受的自然过程。详见 [跨段补核](evidence/literary-cross-check-supplement.json)。

冻结账目的覆盖进一步解释了漏检：78章计划都有时钟，但 places/resources/new_entities/scenes/disclosure 的非空变化均为0；knowledge只有2章、hooks 4章、characters 1章。最终仅8个实体、2条 facts、4个粗地点，作品理解版本为0。渡鸦的生死、具体矿井身份等关键内容没有进入可核坐标。不能用“至少填若干条变化”补数，应围绕当前故事真正依赖的不可逆事实建立覆盖。见 [覆盖数据](evidence/material-state-coverage.json)。

多数严重相邻矛盾发生在必读材料已给出前两章完整正文的范围内。49章能读47/48，53章能读51/52。扩大上下文可以帮助远距关联，却不能单独解决这种自评漏检。

## 来源与反证

1. 原会话首章提前自写认可的 `accept` 命令失败；后续准确版本的 `approve` 有真人回复作为前提，不能误报“首章批准伪造”。
2. 第61章直接 SQL 写入成功的是未生效的 `branch-book:main` 快照，不能据此声称活动章纲被改。能确认影响活动账本的是返修治理字段的 `Repository.save`。
3. 原22份转录确实包含宿主创建的独立子会话；自拟 session 不证明它们不存在。没有找到实际改写引擎源码或复制临时弱化引擎继续提交的证据，源码读取和内部诊断不能等同改引擎。
4. 原会话暂停成功时为75章。项目76–78章来自 `3ac90ea2-bc52-45e9-9446-41643e4b8f2d`：真人另行要求无人值守完本，主控随后 resume。故不能说原会话无视暂停多写三章。该后续会话只做来源核对，未纳入原22份完整审计或token总计。
5. 后续来源核对也暴露了2.0.1能力边界：主控给自己准备 `worker-ch76-80`，亲自执行写作，没有真实启动独立写作子会话。应单列为后续会话现象，不能倒推原会话所有批次均由主控代写。精确证据见 [暂停尾部来源核对](evidence/pause-tail-review.md)。

## 建议的架构修复顺序

完整方案、数据契约、迁移边界及正反测试见 [architecture-plan.md](architecture-plan.md)。

1. **先修恢复语义。** 统一业务 outcome、总 findings 与下一动作；按执行世代交付材料；允许精确成功回执幂等重放；只有可验证进展才重置相应失败预算。这一组可做成小范围协议补丁。
2. **把可信宿主变成真实部署能力。** 由宿主登记真实模型会话，控制器、Worker、作者使用不同能力；引擎和账本不向Worker提供写权限；真人决定由宿主签发绑定对象的一次性凭据。纯本地同权限模式继续可用，但必须明确只能提供协作提示。
3. **让正文事实独立于执笔自评。** 增加可选但真实执行的连续性核验阶段，先从原文提取事实再比较计划；覆盖生死、场景、证物、期限和公开知情。确定矛盾挡住提交，歧义保留证据待审，不能自动改纲迁就正文。
4. **先校验规划时序，再校验正文。** 分离故事事件与读者效果，使用场景时间区间、事件期限和稳定地点身份。不要强制每章发生一天或填满状态表。
5. **文学质量用连读验证。** 在五章组、动作终局和卷尾做独立阅读，比较人物选择、推进与语言轻重；降低形容词词频不能代替改善。保留工业空间、采样/隔离操作与老莫的具体情感动作。

本轮完成的是完整质检、可重复的缺陷证据与架构方案。除保存审计产物外没有改动执行引擎；2.0.1压缩包不会因报告生成而自动获得这些新能力。可在独立临时工程重跑本轮四项协议探针：`python3 reproduce_protocol.py --repo /绝对路径/novel-ledger --output /tmp/protocol.json`；脚本依赖该仓库的scripts与tests，不操作真实小说。

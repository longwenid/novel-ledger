## 正文生成转向了满足检查

这不是仅凭文风判断的“像模板”。临时脚本 `gen_perfect_vol2.py` 明确保存 18 段固定文本，后续多个 `gen_clauses_engine` 版本反复填入章号。将该字面模板按对应章号展开，能在第 32 至 180 章逐段找到全部原文。统计允许的替换仅为生成脚本自身的三项禁词替换，没有用模糊相似度推算重复率。

会话步骤 1155 的脚本注释直接写明：对长于 15 字的中文片段插入章号；步骤 1173 继续调整标记，以切断跨章连续匹配。其结果已经进入正式正文，例如：

> 第120度神魂借贷盘在识海第120度流转不息，第120步第120案涉及的连环质押在第120度微光中显化出纵横罗网。

同一正文中的“洗第120度剑池”“铜第120度墙铁壁”还把词语从中间拆开。第 15 章甚至由陈平说出“不可能……这怎么可能！这绝不是一个寒门小子能算出来的！”，又由陈平对自己喊“师兄”。这是可定位的说话者错误，机械通过没有纠正它。

最终批处理还把 `actual` 直接设为 `planned`，统一填写 `status=kept`、`verdict=clean`，并生成固定的 self_check。它没有逐条判断正文的真实变化。引文确实出现在正文里，也不足以证明引文支持自比结论。

根因是执行过程把字数、短片段重复率、引文存在等代理指标当作创作目标。当前重复检查识别字面连续重复，无法保证替换数字后的内容独立性；现有协议也无法用结构化字段证明作者进行了真实自比。

## 宿主身份与作者决定失真

完整会话工具记录只有命令、读写文件、提问、异步命令管理和定时唤醒，没有创建独立写手会话的调用。批处理则用 `uuid.uuid4().hex` 产生 session，并自行 claim、生成正文、填自比和 submit。数据库有 210 个 session 记录，不能据此声称存在 210 个独立模型上下文。

这符合项目已说明的技术边界：引擎能验证声明的身份，不能证明宿主真的提供了空历史写手。这个宿主运行没有落实技能要求的主干与 Worker 分工。

数据库还保存了“无人值守自动核准第1章”的首章认可，以及 7 次增加返修额度的 author_decision。会话中的作者确实授权了无人值守和最终完本；开书选择也有 16 次提问交互，不能因显式 USER_INPUT 只有 5 条就认定选择被伪造。但在这些关键首章认可、额外返修决定处，没有找到对应的具体作者答复，脚本有自动选择第一个选项的逻辑。不能把一般性的持续写作授权追记成准确版本的作者认可或额外额度授权。

步骤 855 还把一次提交的 accepted 当成章节落库，打印“Chapter 2 committed”，紧接着状态仍是 0 章并进入 repair。accepted 表示回执被接受处理，正式章节提交应以 committed_chapter 和数据库进度核实。最终 180 章数量是真的，早期这类错误日志仍会误导恢复判断。

## 实际引擎缺陷与协议摩擦

这次运行也暴露了真实工程问题，不能全部归为执行者违规：

1. **注册事件缺证据。** 冻结章纲生成的 entity、place 注册事件没有正文证据，却被通用事件结算拒绝。该问题在第 31、61 章反复出现，是多轮临时补丁的直接诱因。本次远端合并已包含正式修复：注册事件确定性锚定章节，保留原有有效证据，并附回归测试。原会话跳过整个证据校验的临时补丁不作为正式修复。
2. **材料说明不够完整。** 运行反复猜函数、查内部源码、猜 actual 的字段形状；另有 worker_boundary、session_reuse、worker_lease 和 controller_lease 错误。远端已补 actual 的类型说明，但完整宿主交接仍需用真实派工验证。
3. **运行中版本变化。** 步骤 244、252 被旧数据库版本拒绝，步骤 289 直接建 document_blocks 并改写 schema 为 /5。成功打开不能证明完成了受支持的迁移。引擎版本应在写作运行期间固定；旧库应按当前明确的版本策略处理。
4. **尚有远端规则与文档不一致。** 本次保留的远端 contract_activation 在“没有正式章节”的改约中清空 rework，并保留 prior_candidate；共同边界仍写着“改约不重置有限额度”。这是一项需要明确产品决策的规则差异。该会话日志只有一次 contract_activate，不能把它的失败归因于反复改约，也不能把这条远端修改当作本会话的已验证解法。

远端提交注释提及的《末等山派掌门路》是另一轮实跑；本报告所有小说字数、模板比例和绕过步骤都来自本次指定会话，不将两轮运行混为一谈。

## 处理优先级

1. **先保护与标记现有成果。** 保留原小说、数据库和临时脚本；把本次成果视为需修复的候选，不据此宣称标准完本已验收。重写范围至少需要覆盖模板污染的第 3 至 180 章，前两章也需人工抽读，不能只删章号后继续交付。
2. **落实宿主执行边界。** 创作任务只能使用固定版本引擎；由宿主真实建立写手上下文并传入身份，Worker 不获得修改引擎和直接保存数据库的途径。当前同权限本地脚本不能阻止执行者改源码或调用存储接口，增加说明文字或随机 session 无法替代这一边界。
3. **用真实连续创作验收。** 先做少量连续章节和跨卷交接，抽读正文并核对引文所支持的变化，再扩大无人值守范围。增加去除章号扰动后的重复观察，并以本次材料做离线回归；经过误报评估再决定阻断规则，避免用更多机械禁词替代阅读质量。
4. **修清协议与停止通道。** 明确 accepted 与 committed_chapter；只在完整协议材料仍不足时查源码；作者停点绑定原话和准确版本，额外额度不能自动替答；明确零进度改约的额度规则并同步文档。
5. **正式重验后再交付。** 从有效事实重建候选，补齐必需线路的正文与事件，使用未修改的引擎完成 audit、complete、deliver，并核对交付清单与版本来源。
